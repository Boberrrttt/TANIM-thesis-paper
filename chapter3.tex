\section{Requirements Analysis}
The system requires the development and implementation of a machine learning component capable of performing soil health prediction, and  crop recommendation. Machine Learning boosting algorithms was employed for these tasks, using both sensor and zoning data. The sensors collects important soil information such as Nitrogen (N), Phosphorus (P), Potassium (K), pH level, moisture, temperature, and salinity. By obtaining the data sources, the system can better understand the relationship between soil condition and the environment. Based on the collected data, the machine learning model classifies the soil quality levels, while crop yield forecasting will leverage an optimized machine learning model by identifying patterns and relationships between soil parameters and environmental factors. To make predictions more accurate, the model uses a metaheuristic-based feature selection that focuses on the most relevant data and removes unnecessary or less useful information. 
	
After analyzing the soil health parameters and producing crop recommendations, the system generates fertilizer recommendations based on predicted soil nutrient deficiencies, crop nutrient requirements, and established agronomic guidelines. The system determines the appropriate fertilizer type and application rate suited for specific field conditions. To make sure the machine learning model produces reliable results, the dataset was divided into three parts: $70\%$ for training, $15\%$ for validation, and $15\%$ for testing. This ensures that the system learns effectively from the data, maintains accuracy, and avoids overfitting.
	
The system undergoes proper evaluation using both quantitative and qualitative approaches. Quantitative assessment includes metrics such as accuracy, precision, recall, and F1-score for crop recommendation. RMSE, and MAE was used for consistency ratios and ranking stability for soil health readings. Conducting these metric evaluations is important because they measure how well the machine learning model performs and how reliable its predictions are. By analyzing these values, the researchers can identify the model’s strengths, detect errors, and make adjustments to improve performance before deployment. Cross-validation ensures model robustness across different crop zones.Meanwhile, qualitative evaluation involves focus group discussions and structured interviews with farmers and agricultural technicians in Region 10 to assess usability, reliability, and practical value. Feedback from these sessions will guide further refinement of the system to ensure its effectiveness in real-world agricultural applications.

\section{Data Collection and Processing}

It covers the collection of soil, environmental, and geographical data from various sources, as well as the acquisition of historical datasets. \subsection{Soil Data Collection}
Soil data collection is the main input of the system, providing the information needed for crop recommendation and soil analysis. In this study, the primary dataset used for the machine learning model comes from the Department of Agriculture (DA) Region 10. This dataset includes recorded soil parameters such as nitrogen (N), phosphorus (P), potassium (K), soil pH, moisture, temperature, and salinity.
These records are used to train the Light Gradient Boosting Machine (LGBM) model so it can learn patterns between soil conditions and suitable crops. Since the data comes from verified sources, it helps improve the accuracy and reliability of the model.

In addition, the system is designed to support IoT-based soil data collection using sensors connected to an ESP32 microcontroller. These sensors can measure real-time soil conditions in the field. However, in the current implementation, this data is mainly intended for crop recommendation and for future dataset expansion rather than for training the model.

Overall, the soil data collected from the DA serves as the foundation of the system, while IoT integration provides an opportunity to improve real-time analysis for crop recommendation and enhance the dataset in future developments.

\subsection{Environmental and Weather Data Collection}
Soil and simple environmental readings from the field are sent to the ML service as one list of numbers. The first values match what the crop model was trained on (organic matter, phosphorus, potassium, and pH). If the device sends more values, those can include things like temperature, moisture, and electrical conductivity. After each prediction, the system saves a pending snapshot that holds the numbers, the full request, an optional farm id, and optional latitude and longitude. The app can then pull that single snapshot instead of combining data from many separate calls.

Weather works differently. The project does not use a weather station on the farm. The backend talks to OpenWeatherMap using lat and long, keeps the API key on the server, and sends the app a clean package with temperature, humidity, pressure, wind, visibility, a short description of the sky, the place name, and a time stamp. The app does not need to hit the weather API constantly, so it can cache results for a short time. Which coordinates are used matters: if the latest ML request already had lat and long, those are used for weather so it matches the same area as the sensor run. If not, the app uses the coordinates stored for that farm. There is also an optional fallback for testing when coordinates are missing. When the farmer has an active saved session, the screen shows the saved soil data from the server for consistency. When there is no active session, the app checks often for new pending readings so the numbers stay up to date.

This setup is intentional. Soil measurements and internet weather are not the same thing, but showing both together gives a clearer picture. Putting the weather API on the backend hides the key and keeps responses in one standard format. Using one feature list and one pending snapshot keeps the model, the server, and the app on the same page and avoids extra work in the mobile client.


\subsection{Zoning and Geographical Data Collection}
Geographic representation matters so farm records are not just names on a list but real places on the ground. The system needs to know where farming happens, roughly how big the holding is, and stable coordinates that other tools can use, such as weather APIs and machine learning workflows. Right now, location is stored mostly as a point: each farm can have latitude and longitude, plus an optional text field for things like barangay or street, and a field for how large the farm is said to be. Admins and users enter this through the web when they create or edit a farm. The API can also update coordinates when a session or a sync from the model layer brings in new positions, so people do not have to fix the map by hand as often.

In this study, the term “zoning” means organizing farms in space, not official land-use zones drawn as polygons on a cadastral map. The admin GIS Mapping screen shows farms on a Leaflet map with OpenStreetMap tiles. Farms with real latitude and longitude show up as pins. Farms without coordinates stay off the map until someone adds GPS data, and the UI warns you if registered farms still have no usable GPS. If there is more than one farm, the map zooms to fit all the pins. The default map center fits the Philippines so the first view is not empty. Clicking a pin shows extra details like soil type and area so you can relate the site to soil conditions. Soil tests are linked to the same farm id, so lab or field results line up with that place in the dashboard

By centralizing disparate information into a uniform structure, the system ensures that the predictive models can process environmental, and historical variables simultaneously. This integration is essential for creating a holistic representation of the agricultural environment, bridging the gap between local sensor observations and broader regional contexts.

As illustrated in the integration pipeline in Figure \ref{fig:integration_pipeline}, the system aggregates data from external sources. The pipeline depicts the convergence of LoRa-based sensor data, REST-based weather APIs, and batch-imported historical records into a unified dataset. Real-time data is captured via an ESP32 IoT sensor node, which transmits continuous readings of Nitrogen (N), Phosphorus (P), Potassium (K), pH levels, soil moisture, and temperature. These hardware-derived metrics are combined with external data streams, including localized weather updates retrieved through HTTP/REST APIs and the validated Consolidated Soil Info (RSL) 2023--2025 historical dataset. This multi-source approach allows the framework to factor in both immediate soil conditions and long-term agricultural trends.

To ensure contextual accuracy, the system employs rigorous temporal and spatial synchronization. Data ingestion occurs through different protocols depending on the source: LoRa transmission for hardware sensors, RESTful requests for weather data, and batch imports for historical records. \subsection{Data Preprocessing}
The primary objective of data preprocessing within this framework is to systematically refine and clean the integrated dataset, thereby reducing algorithmic bias and ensuring high accuracy during the subsequent machine learning training phase. Given that the machine learning models rely on the structural integrity of the input data to generate reliable crop and fertilizer recommendations, this phase acts as a critical filter. It transforms raw, heterogeneous data into a standardized format that facilitates efficient mathematical computation and pattern recognition. 

The initial stage involves rigorous data cleaning to address missing or empty values. As illustrated in the sequential pipeline in Figure \ref{fig:SequentialPreprocessingPipeline}, these gaps are handled based on the statistical variation of the feature. Depending on the feature's distribution, these gaps are addressed through mathematical substitution, such as applying the feature mean or using linear interpolation, or through the systematic removal of records showing excessive missing data to maintain dataset integrity.

Following the initial cleaning, noise and outlier handling mechanisms are applied to filter unusual data points generated by temporary sensor glitches or transmission errors. This process employs statistical limits, specifically Z-score thresholding, to identify and discard extreme values that could otherwise skew the decision boundaries of the model. The preprocessing pipeline concludes with comprehensive programmatic consistency checks to definitively verify the structural integrity and uniformity of the cleaned dataset. This final audit ensures that all processed records adhere to the predefined schema and that no data corruption occurred during the transformation stages. \subsection{Feature Engineering}
The primary objective of the feature engineering phase was to augment the predictive performance of the machine learning models by providing more nuanced and expressive data representations. Rather than relying exclusively on the raw soil properties captured through the sensor network and historical datasets, this phase involved mathematically deriving new variables that encode established agronomic relationships. By transforming raw measurements into high-order features, the system enables the algorithms to capture complex, non-linear dependencies between soil chemistry and plant health that are not explicitly present in the initial input vectors.

Two distinct categories of derived features were constructed for the engineered dataset. The first category comprised ratio-based features designed to quantify the balance between specific nutrients. The Phosphorus-to-Potassium ratio ($P/K$) was calculated to define the internal nutrient equilibrium between these two primary macronutrients, which serves as a critical fertility indicator in tropical soil profiles. Additionally, the Phosphorus-to-Organic Matter ratio ($P/OM$) was computed to express Phosphorus availability relative to the soil's organic composition, reflecting the established agronomic dependency of Phosphorus mobility on organic matter levels.

The second category consisted of interaction features, derived through multiplicative operations to encode conditional relationships. An Organic Matter $\times$ pH interaction term was generated to represent the principle that organic matter decomposition and subsequent nutrient release are strongly regulated by soil acidity. Similarly, a Potassium $\times$ pH interaction term was derived to capture the pH-dependent nature of Potassium uptake by root systems. These interaction terms allowed the model to learn complex interdependencies without requiring manual thresholding or excessively deep neural architectures.

The explicit encoding of these soil-crop relationships reduced the computational complexity required for the model to discover such patterns independently. By providing calculated nutrient ratios and pH-dependent interaction terms, the algorithm leveraged domain-specific knowledge directly, resulting in faster convergence during the training phase and improved generalization when processing unseen soil conditions. This engineering process successfully expanded the dataset from the four original raw variables to a comprehensive set of eight predictive features.

This phase represents the transition from static data storage to an active learning format, where information is structured to minimize bias and maximize the model's ability to generalize across diverse agricultural scenarios.

A fundamental component of this phase is dataset splitting, where the unified data is stratified to maintain representative class distributions across all subsets. As illustrated in Figure \ref{fig:DataSplit}, the dataset is divided into three definitive partitions: 70\% of the data is allocated for direct model training, 15\% is utilized for validation to systematically tune hyperparameters, and the remaining 15\% is strictly reserved for blind testing to evaluate final real-world performance. \subsection{Data Storage and Management}
The architecture of the proposed system necessitates a centralized and reliable repository to ensure data consistency across administrative and end-user platforms. This repository facilitates the management of diverse entities, including farmer and administrator accounts, farm records encompassing geographic coordinates and land area, active farming sessions, and soil test readings. Furthermore, the database stores the outputs of the machine learning engine, specifically crop and fertilizer recommendations, alongside system telemetry and device status updates. While machine learning models are maintained as distinct training artifacts, all operational and longitudinal data are housed within the database to ensure that the web dashboard, mobile application, and backend services utilize a unified source of truth.

The system utilizes a standard relational database management system, specifically PostgreSQL, which is deployed via a managed cloud service to ensure high availability and automated maintenance. The backend Application Programming Interface (API) establishes a secure connection to the database, organizing data into structured tables for users, farms, sessions, soil tests, and recommendations. To optimize schema complexity, richer nested data structures are stored using structured fields within the relational environment, reducing the need for an excessive number of auxiliary tables while maintaining query efficiency. The mobile application interacts with this layer through standard HTTP requests, while the web application leverages a Representational State Transfer (REST) layer provided by the hosting service to streamline Create, Read, Update, and Delete (CRUD) operations without schema duplication.

Security and scalability are integral to the data management strategy of the system. User authentication is secured through strong cryptographic hashing for passwords, while session management is handled via a dual-token system consisting of short-lived access tokens and longer-lived refresh tokens. These tokens are stored within secure on-device storage on the mobile platform and verified against secrets maintained in the server configuration. Furthermore, the hosting environment implements Row-Level Security (RLS) policies to ensure that users are restricted to accessing only their authorized data subsets. To accommodate increasing traffic and data volume, the system employs connection pooling, stateless API instances capable of horizontal scaling behind a load balancer, and paginated data retrieval to minimize latency and server overhead. Consistent data integrity is maintained through automated backup protocols managed by the database provider, ensuring recovery in the event of system failure.

\subsection{Data Processing Workflow}
	The TANIM system employs a multi-stage data pipeline designed to transform raw environmental signals into actionable agricultural intelligence. This workflow integrates physical sensing, cloud-based data management, and advanced machine learning analytics to provide decision-support tools for both farmers and regional agricultural authorities. 
	
	\begin{figure}[H]
		\centering
		\caption{TANIM Data Processing Workflow Pipeline}
		\includegraphics[width=0.7\textwidth]{figures/DataProcessingWorkflow.png}
		\label{fig:DataProcessingWorkflow}
	\end{figure}
	
	Figure \ref{fig:DataProcessingWorkflow} illustrates the comprehensive data flow, from initial acquisition to end-user dissemination, following a logical progression through hardware interfacing, cloud integration, and predictive modeling. The workflow demonstrates the transition from raw sensor acquisition to the generation of agricultural insights.
	
	The primary stage of the workflow involves the high-fidelity collection of soil parameters at the physical layer. The system utilizes a multi-parameter soil sensor to monitor Nitrogen (N), Phosphorus (P), Potassium (K), pH, moisture, salinity, and temperature, all of which are interfaced with an ESP32 microcontroller. To ensure data integrity during local transmission, a MAX485 module is employed to convert RS-485 differential signals to TTL-compatible logic for the microcontroller. These data packets are subsequently encapsulated and transmitted via the LoRa (Long Range) protocol to a central gateway. This modulation technique is specifically selected to ensure reliable connectivity in topographically challenging or remote agricultural zones where traditional cellular infrastructure is often insufficient.
	
	Upon receipt at the gateway, the data is forwarded to a Firebase cloud database for centralized management and refinement. During this phase, the system performs rigorous data cleaning by executing filtering algorithms to mitigate electrical noise and remove statistical outliers from the raw sensor readings. Furthermore, a data fusion process contextualizes the real-time sensor data by integrating it with secondary datasets. These include meteorological information, such as precipitation and humidity acquired via external APIs, and geospatial zoning maps provided by the Department of Agriculture (DA) Region 10.
	
	The analytical core of the system leverages a LightGBM algorithm, a gradient boosting framework utilized for its high efficiency and superior performance with tabular agricultural datasets. The process begins with metaheuristic-based feature selection to identify the most significant soil and climatic variables, thereby reducing dimensionality and improving model generalization. The predictive engine then performs dual-task analytics, which include classifying soil health status based on established agronomic thresholds and forecasting crop suitability to optimize regional yield performance.

	\subsection{System Architecture}
	\begin{figure}[H]
		\centering
		\caption{System Architecture}
		\label{fig:SystemArchitecture}
		\includegraphics[width=1\textwidth]{figures/finalSYSARCH.pdf}
	\end{figure}
	
The \textbf{Figure \ref{fig:SystemArchitecture}} shows the updated system architecture for the Soil Health Monitoring, Fertilizer, and Crop Recommendation System (TANIM). The system goes from hardware in the field, through a LoRa link and a local gateway, into the cloud for storage and machine learning, and then out to a web app for agricultural authorities and a mobile app for farmers.
Field IoT device. The sensing unit is basically one IoT package in the field. A solar panel feeds a solar panel manager, which handles charging and power so the device can keep running in areas that are far from the grid. Inside the box, an ESP32 reads the sensors, does any simple processing on the readings, and builds the packets that will be sent out.

A soil sensor measures things like NPK, pH, and moisture. The sensor talks over an industrial serial link that behaves like RS-485, which is good when the cable is long and the environment is noisy. A TTL MAX485 module turns that into a regular UART signal the ESP32 can read, so you get reliable communication without making the firmware too complicated.
The device also has a GPS module. The ESP32 reads the GPS data and sends location together with the soil readings. That way the cloud and the TANIM Web App can show maps and trends by area, not just a list of numbers with no place attached.

The ESP32 sends data through a LoRa module. LoRa is meant for low power and longer range, which fits farms and rural sites.
Gateway and path into the cloud. A LoRa receiver listens for packets from one or many nodes in the field. It is connected to a second ESP32 that works as a gateway. That ESP32 receives the LoRa traffic, checks the data, can hold or reshape packets if needed, and then sends everything upstream. The forwarded data includes soil readings, and GPS location.

Cloud, machine learning, and apps. After the gateway, the system splits into two main parts in the cloud. One part is machine learning, which uses new data and past data to look for patterns in the soil, spot possible problems like low nutrients or moisture stress, and suggest fertilizers, crops, and simple soil health takeaways. The other part is Supabase, which is the main backend for the project. Supabase stores data in a database, handles sign in and users, and exposes APIs for things like sensor history, profiles, and who is allowed to see what, especially for authority users.

The TANIM Web App is built for agricultural authorities. It uses Supabase for the underlying data and adds views like dashboards and maps, plus results from the ML side where those are wired in. The TANIM Mobile App is built for farmers in plainer language: soil insights, recommendations, alert. Both apps use Supabase for secure access to stored data and connect to the machine learning side when the app needs model based recommendations.

	\subsection{Entity Relationship Diagram}
	The relational architecture of the database is designed to provide a structured and scalable environment for managing agricultural data through four primary entities: Admin, Farmer, Farm, and Farming Session. As illustrated in Figure \ref{fig:ERD}, the Admin entity serves as the administrative oversight layer, storing unique identification and authentication credentials for system-wide management. The Farmer entity represents the primary endusers of the platform, containing detailed profile information including full names, contact numbers, and secure login credentials. This entity is linked to the Farm table through a foreign key ($farmer\_id$), establishing a one-to-many relationship that allows a single farmer to register and monitor multiple distinct agricultural plots. Each farm record preserves critical metadata such as the plot name, physical area measurement, and precise geographic coordinates (latitude and longitude) to support spatial mapping
	
	\begin{figure}[H]
		\centering
		\caption{Entity Relationship Diagram}
		\label{fig:ERD}
		\includegraphics[width=1\textwidth]{figures/erd.pdf}
	\end{figure}
	
	The Soil Health Test entity stores discrete, time-stamped soil measurements for a given farm. Each test row is identified by a primary key ($test\_id$) and is linked to the Farm table by a foreign key ($farm\_id$), in a one-to-many relationship: one farm can have many soil health tests over time. The entity records macronutrients—nitrogen, phosphorus, and potassium—together with pH, salinity, temperature, and moisture, and it maintains created\_at and updated\_at timestamps for each record so the system can keep a verifiable history of how soil conditions evolve for that plot.
	
	Operational data and model-driven insights are managed within the Farming Session entity, which functions as a temporal log of field activity. This table acts as the nexus of the system, linking a specific farmer to a specific farm for the duration of a planting cycle. Rather than storing soil data as static attributes of a land plot, the system archives discrete “soil snapshots,” fertilizer recommendations, and model-generated top crop probabilities within the session record. This design allows the system to maintain a historical archive of soil health and decision-making for every visit or cycle. The session record also captures the user’s final decision in the selected crop field and 93 tracks the timing of the cycle through start, end, and creation timestamps. This normalized structure ensures data integrity while supporting complex longitudinal queries regarding farm performance and historical soil trends.

\section{Implementation}
The Implementation phase involves developing the software and hardware components. Each function was ensured to function according to the design specifications.This phase intends to transform the conceptual design into a working prototype that can perform data acquisition, processing, and output for TANIM.
	
\subsection{Software Implementation}
The software implementation for TANIM is designed to provide an efficient, reliable, and user-friendly platform that caters to the needs of both the Farmer and the Department of Agriculture. To ensure optimal accessibility and performance, the frontend for farmers is developed using React Native, a framework well-suited for creating responsive and cross-platform mobile applications. The mobile application also features offline data handling, allowing farmers to access previously synced soil and crop data even without an internet connection. Any new inputs or updates made while offline are temporarily stored locally on the device and automatically synchronized with the cloud once connectivity is restored. This ensures uninterrupted functionality in rural areas with limited network coverage.
	
Meanwhile, the frontend for the Department of Agriculture is implemented using React.js, providing a seamless and interactive web application experience. The web application integrates advanced analytics and visualization tools, enabling agricultural authorities to interpret soil data, monitor farm conditions, and analyze regional agricultural trends through interactive charts, dashboards, and geospatial maps. These insights support data-driven planning, resource allocation, and policy formulation.
	
Both user interfaces interact with a shared backend developed in Flask, which centralizes data management and ensures consistent functionality across platforms. This architecture enables efficient communication between the mobile and web applications while supporting scalability, maintainability, and ease of integration with additional features or services in the future.
	
\subsection{Hardware Implementation}
The hardware implementation of the TANIM system is centered on an IoT-based device designed to collect soil data and send it to the cloud for processing and analysis. The core of the device is the ESP32 microcontroller, selected for its high processing capability, built-in Wi-Fi and Bluetooth connectivity, low power consumption, and compatibility with multiple sensor modules. These features make it ideal for continuous field monitoring and data transmission in remote agricultural areas.
	
A 7 in 1 soil sensor was used to measure key soil parameters such as pH, NPK, moisture, temperature, and salinity. This sensor was chosen because it provides accurate and real-time soil data essential for evaluating soil health and guiding fertilizer and crop recommendations.

A GPS module provides geographical localization data, essential for mapping sensor readings to specific field coordinates. For long-range data transmission in remote agricultural areas, a LoRa module is integrated as the system's transmitter, enabling robust, low-power wireless communication. Additionally, an I2C-LCD displays instantaneous sensor readings locally for immediate field-level monitoring.
	
\subsection{Machine Learning Model}
The TANIM project used a LightGBM model because it processes data quickly and accurately sorts information into different categories. Since regional soil data often has uneven amounts of information for various soil types, the system applies a K-Means method to address this imbalance. This method generates additional data for the underrepresented groups, creating a balanced dataset for the model to learn effectively.

The program evaluates key soil elements, specifically organic matter, phosphorus, potassium, and pH levels, to assess soil health and predict the most suitable crops for a given area. By combining the LightGBM model with a balanced dataset, the system improves prediction performance and provides reliable agricultural recommendations.

\section{Test and Evaluation}
Testing and evaluation was conducted to verify the system’s effectiveness, accuracy, and usability for crop recommendation and soil health monitoring. This process was designed to ensure that the hardware components, software components, and machine learning models functions according to what we aim for this study, which involves hardware testing and calibration, functional testing, system integration testing, performance testing, and usability testing. Hardware testing and calibration focuses on verifying the accuracy of the sensors to ensure reliable soil data. Functional testing examines whether the mobile and web applications operate correctly and deliver the expected outputs of each feature. To ensure that the hardware, cloud database, machine learning, and applications works together with proper data flow and error handling, system integration was implemented. For measuring the responsiveness of the system and to evaluate the system’s predictive accuracy of the machine learning models using various performance metrics we be conducting performance testing. Moreover, usability testing was used to assess the practicality and user-friendliness of the system by involving farmers and agricultural experts in field trial and feedback collection.

On the other hand, To validate the nutrient measurements, the team employed a Soil Test Kit (STK) method to compare sensor output against established agronomic thresholds. Specifically, sensor readings for Nitrogen, Phosphorus, and Potassium were cross-referenced with the STK results to see if they consistently fell within the same qualitative categories of low, medium, or high. For instance, a sensor reading for Potassium would be evaluated against a predefined range where values below 117 ppm are categorized as low and those above 235 ppm are considered high. This threshold-based verification allowed the team to confirm that the hardware system provides reliable categorical data suitable for crop recommendation despite the lack of high-level technical calibration tools.

	
\subsection{Functional Testing}
Functional testing involves verifying whether each feature of the mobile and web applications operates correctly according to the system design. For the mobile application, the following features was tested: secure login and authentication, retrieval of soil health readings, display of crop recommendations for multi-cropping, fertilizer optimization, and offline data synchronization. For the web application, features such as farm visualization, farmer profile management, and farms GIS mapping was tested.
	
In addition, synchronization between the database, mobile, and web applications was tested to ensure that all data are accurately updated and consistent across platforms. This includes verifying that soil readings, user information, and crop recommendations are properly synchronized when data are sent or retrieved from the cloud.
	
Both black-box testing and white-box testing approaches was applied to evaluate the system’s functionality. Black-box testing focuses on verifying the system’s external behavior without examining its internal code. Testers inputs various data to check if the outputs match the expected results, ensuring that all functions operate as intended from a user’s perspective. Meanwhile, white-box testing was conducted by examining the internal logic, data flow, and code structure of the applications. This helps identify hidden logical errors, broken functions, or inefficient code implementations.
	
\subsection{System Integration Testing}
System integration testing evaluates whether the hardware, software, cloud database, and machine learning model communicates seamlessly with each other as a single system. The system integration testing was tested by following the full flow of the system: soil health readings captured by the sensor and processed by the ESP32 microcontroller, then transmitted by via the LoRa module to the gateway, forwarded to the cloud database, then processed by the machine learning models, and finally displayed on the mobile and web applications. 
	
This process confirms that the system works together as one reliable system. Furthermore, several test was conducted to observe how the system handles incomplete or corrupted data to ensure that it can manage error to prevent misleading recommendations to farmers.
	
\subsection{Performance Testing}
For the system level performance, it is to determine if the system could handle multiple data acquisition and provide timely feedback to the users. The data transmission success rate was monitored by comparing the successful sensor to cloud uploads against the attempted uploads over multiple trials. Latency tests measure the time from the sensor data capture to its display in the mobile and web application, with an acceptable range set to 30 seconds. Scalability was evaluated by simulating multiple farms connected simultaneously to ensure that the cloud database and applications could handle increased workloads without delays and crashes. These ensures that the system is reliable and efficient under real-world agricultural conditions where multiple users operate.
	
For the machine learning evaluation, it verifies the predictive capability of the machine learning models that will be used on crop recommendation for multi-cropping and fertilizer optimization. The dataset will be split into 70-15-15 for training, evaluation, and testing for maximizing the predictive accuracy and avoiding overfitting.

\subsection{Usability Testing}
	The usability testing assesses the accessibility, and user satisfaction of the system. For this, farmers was asked to use the mobile application, review soil health data, view crop and fertilizer recommendations, and simulate updating their farm records. Meanwhile, DA officials use the web dashboard to access farmer profiles, view GIS-based maps, and farm profiles.
	
	A total of 10 participants was involved in the usability testing, consisting of 7 farmers from Region 10 and 3 agricultural technicians or DA employees. Farmers were selected based on their familiarity with basic smartphone usage and their active involvement in small- to medium-scale farming. The DA personnel were chosen because they represent the system’s administrative users responsible for monitoring and validating agricultural data. This mix of participants ensures that both end-user and administrative perspectives are considered during evaluation.
	
	After completing the navigation of the system, the System Usability Scale (SUS) developed by Brooke (1995) was employed to quantitatively measure user satisfaction. The interactions of the users was observed, and any difficulties they encounter was recorded. In addition to the SUS scores, qualitative feedback was collected through short interviews and observation notes to gain insights into which features are most useful and which aspects require improvement. The evaluation criteria determines the user satisfaction based on the SUS scores and user feedback. The result of this testing determines the system's usability rating and this will be a guide for further refinement to ensure that the TANIM system is accessible, user-friendly, and beneficial to the users.
